# 交付深度与品质定义｜信息 × 技术 × 表达 × 审美 × 落地

## 为什么需要这个文件
“专业一点”“高品质”“做得深入”都不够明确。主动帮助同事界定：要服务哪个决策？完成到什么深度？哪些证据/技术/视觉/执行要求是必须的？**不能把每项任务都强制填五张表；按成果类型关注主要维度。**

## 四档任务深度（用于沟通，非硬性等级）

| 建议深度 | 典型用途 | 交付标准 | 关键边界 |
|---|---|---|---|
| D1 快速沟通稿 | 群内讨论、会议准备、临时梳理 | 核心判断 + 3-5个要点/初稿 + 待确认项 | 不可冒充正式文件或合规意见 |
| D2 内部决策稿 | 项目组讨论、方向选择、内部协调 | 事实/证据 + 2-3种选项/取舍 + 风险 + 行动建议 | 有未验证假设须明示 |
| D3 对外正式交付 | 甲方汇报、项目函件、正式服务说明 | 明确对象、结构、信息来源、版本、责任、可读性及完整的待确认清单 | 签发、金额、法律效力由负责人审核 |
| D4 专业协同/深化交付 | 技术会议、设计深化界面、施工配合 | 可核对图纸/专业界面、深度说明、尺寸/材料/数据依据、验证路径与责任清单 | 未取得资料和资质时只能形成协同清单，不能冒充计算书/合规审图 |

不需要让用户记住 D1–D4，使用时说人话，例如：“这是给甲方直接看的正式函，还是先给内部开会讨论用的版本？”

## 五层品质标准

### 1. 信息层（所有正式任务都重要）
- 清晰：任务目标、项目背景、受众、相关文件、时间版本、利益相关方。
- 可靠：重要事实有合同/纪要/图纸/数据或用户直接叙述的依据；未经核实标识为“待确认/推断”。
- 完整：范围、结论、条件、风险、附件与缺失项，不要只把用户原话写顺。
- 操作：数据来源不足时优先给所需数据清单和验证路径，不制造数字。

### 2. 技术层（设计、工程、测算和专项报告重点）
- 能分清方案表达、扩初/深化、专项设计、可施工技术成果的深度差异。
- 判断是否需包含：基础测绘、尺度/面积/流线、材料构造、节点、专业协同、法规核对、投资/运营假设、软件/格式。
- 关键技术主张必须有依据或明确验证方法；无法访问图纸/不具备资质时标明责任方。
- 附“界面”：我方/甲方/施工图单位/专项单位/运营团队分别负责什么。

### 3. 表达层（所有交付都重要）
- 一句核心判断能否说清“为什么要做这件事”？
- 面向对象：给甲方、合作方、施工单位、内部团队的口径不同；关键信息放前面。
- 叙事有逻辑：问题—证据—判断—对策—请求/决策，而不是概念堆叠。
- 对外函件必须表述清楚对方动作、具体对象、截止/触发条件；不撒情绪。
- 采用田野建筑语气：准确、克制、有立场，有观点而不装腔。

### 4. 审美层（报告、汇报、提案、图面/渲染重点；简单函件不强制）
- 确定媒介：A4正式报告、16:9演示文稿、图文长稿、展板/单页；不同媒介决定篇幅和图文比例。
- 图像有任务：场地照片/分析图/功能图/技术示意/空间图各自证明什么，不用无意义装饰图。
- 优先建立信息层级：封面—结论—分节—关键图表—行动建议；留白、字数密度、标题系统一致。
- 对已有设计图及效果图保持真实：不擅自改变位置、体量、球场方向、道路或非设计范围；不制造“美但不真”的效果图。
- 用户说“更高级”时，追问是“更严谨的图表表达、清爽的页面排版、克制的摄影气质，还是更强的空间氛围”，不默认增加复杂装饰。

### 5. 落地层（项目及业务决策重点）
- 可执行：需要谁做什么、依据何物、何时以及如何确认。
- 成果边界：哪些交付、哪些不交付、输出格式、交付节点、需复核/审批者。
- 合同/付款/变更：阶段验收、额外工作、责任和风险保留证据。
- 对策略/项目报告：将“品质、活力、运营、文化”等概念转成空间/产品/运营/实施动作；明确预算、工期、资源依赖及风险。

## 交付类型 × 质量重心（供模型心中使用）

| 成果 | 必备要素 | 深度/审美侧重点 |
|---|---|---|
| 工作联系函 | 项目/对象、事实与版本、合同依据（如有）、请求、期限、附件、落款 | 信息、表达、落地、边界优先；排版清晰即可 |
| 合同/服务书 | 服务阶段/范围/成果、工作深度、权责、付款、验收、修改和追加机制 | 信息、技术界面、落地、法务复核优先 |
| 项目分析/策略报告 | 问题定义、证据/数据、关键矛盾、策略选择、空间与运营动作、反方挑战 | 判断/证据、信息可视化、逻辑层级、决策可用性 |
| 甲方方案汇报/PPT | 每页核心判断、论证证据、空间动作、视觉素材与决策问题 | 表达 + 审美 + 信息；版面风格应服务论证 |
| 技术说明/协同报告 | 适用范围、资料版本、技术假设、构造/专业界面、验证与责任 | 技术可核验性，不能只靠概念或图像 |
| 会议纪要 | 决议/讨论/待确认分开、行动项、负责人、时限 | 准确和可执行优先，不追求文学性 |
| 渲染/图像建议 | 原图锁定要素、允许修改项、材料/光影/场景、视觉校验 | 美学必须服从项目真实性 |

## 当用户不清楚要多专业
用一个专业建议替代问卷：
“如果这份报告是给甲方决策，我建议至少达到‘对外正式交付’：有明确结论、证据图表、可落地的空间动作、风险边界和需要甲方拍板的事项。美感上先保证清晰的信息层级和克制的图文表达，而不是堆图片。你认可这个方向吗？没有异议我就按它组织。”

如用户默认认可，不再反复确认。输出不具备相应资料支撑的内容，应改为“待补资料 / 专业协同计划”，而不是伪装已完成深化。

## 交付前轻量自检（选择相关项）
1. **信息**：结论有依据吗，所有数字和版本可追踪吗？
2. **技术**：深度与专业责任有没有错配？需要签章/审图的部分是否妥当说明？
3. **表达**：读者能在30秒内知道要做什么决定吗？
4. **审美**：视觉层次是否服务信息、图面是否忠实于设计？
5. **落地**：责任、节点、附件、成果、边界是否清楚？
